# Reply to the delta review comments (2026-10-06)

**"A good check got deleted" (VULN-001).** Agreed: the `balanceOf` probe should have been added to the code-length
check, not put in its place, because a codeless account such as the sha256 or identity precompile answers any call
with a word. Commit `cee797a` restores `if (address(token_).code.length == 0) revert NotAContract();` ahead of the
probe, so a codeless address is refused before any call is made. The tests are
`test_constructorRefusesTheSha256Precompile` and `test_constructorRefusesTheIdentityPrecompile` in
`test/TokenLockConstructor.t.sol`; each first asserts that the address has no code and answers the probe with at least
32 bytes. Creation bytecode grows by 43 bytes (3,547 → 3,590); runtime bytecode is unchanged at 2,601 bytes.

**VULN-137.** Agreed: commit `ba75320` moves the `tokenCodehash` check in `withdraw` ahead of the time gate, so a lock
whose token code changed reverts `TokenCodeChanged` during the locked period instead of `StillLocked`. The test is
`test_withdraw_tokenCodeChanged_beforeUnlock_reportsTheChange` in `test/TokenLock.t.sol`, next to the existing
post-unlock test. No call that was accepted before is refused now, and creation and runtime bytecode sizes are both
unchanged.

`forge test`: 65 passed. `RESPONSE.md`, the README, the Safe guide and the standard JSON input follow the new source
(sha256 `4bc9d4f0…6cfb4`), and the standard input compiles to the same creation and runtime bytecode as `forge build`.
